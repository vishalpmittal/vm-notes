# Staying Technical as a Manager

A concrete routine for staying hands-on as an EM in the AI era — without drifting back into shipping features.

## Key Takeaways

- **Both extremes are wrong.** Don't code to ship features; don't fully detach either. Target **~5–10% of the week (~4 hrs)** touching the team's codebase — a *ceiling, not a floor*. If it eats into 1:1s or roadmap work, you've lost the plot
- **The goal is empathy, not output.** You're there to feel the team's daily reality and frustrations — not to deliver project work or become the expert
- **AI lowers the cost of staying hands-on.** It teaches an unfamiliar stack by analogy to one you know (author learned Python via his PHP background); it didn't invent hands-on management, it made it cheap
- **Pick safe tasks + a fixed slot.** Low-risk work (no deadline, one service, blocks no one, no downstream impact) in a recurring calendar block

## Actionable Insights

- **Block a fixed recurring slot** (author: 4 hrs every other Friday). Keep a small backlog of low-risk tasks under one epic, sorted simplest → hardest
- **Follow a 6-step AI loop:** (1) learn the repo first with a cheap model → (2) run/touch/break it and ask AI *why* it broke → (3) brainstorm and challenge the plan before coding → (4) self-review via language analogies → (5) run/confirm before the MR → (6) go through the *real* team review and ship
- **AI hygiene:** keep context window under ~60–70% ("context rot"), one session per distinct task, name/archive sessions
- **Match model to task:** cheap/fast model for learning & analysis, mid-tier for planning, top-tier for implementation & review — but default to mid-tier (the biggest model over-engineers simple tasks)
- **Encode your workflow as reusable skills** (e.g., a "review through PHP analogy" Claude Code skill)
